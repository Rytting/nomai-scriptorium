## 五个问题：全部已答

来源：作者博客 https://evanfields.net/Nomai-Writing/
（站点上那个「Blog post」链接指向 evanfields.github.io，会 301 到 .net）

### 编码机制

整条消息当作一个大整数。每个字符的 Unicode 码点是一位数字，`base` 是进制。
作者的例子——`hey` 码点 104/101/121，base 256：

```
104·256⁰ + 101·256¹ + 121·256² = 7,955,816
```

**base 必须大于最大码点**，否则位与位会撞。base 200000 时，
"This sentence has moderate length." 编出的整数超过 10^176。

### ✅ Oracle 的接口

Oracle 消费那个大整数，回答「k 选一」的问题：

```
answer = x mod k
x = x ÷ k
```

生成过程中每个需要做选择的地方问它一次。

### ✅ GlyphGrid 保存了什么

矩形二维网格，存**抽象的字形位置与连接**。网格里有**两条字形路径**，
都从最左列的中间行开始，每次向右延伸一列。

### ✅ glyph 字母表

共 **33 个字形**：前 16 个是基础字形，后 17 个是基础字形加注记
（小方块、一对「角」等）。全部从游戏内样本手工描出。
**注记与否没有语义含义**，作者称其为「vestigial」。

### ✅ 螺旋排版与内部结构的边界

**完全分离。** 矩形网格在排版阶段才映射成螺旋：水平轴 → 螺旋路径，
垂直偏移保持垂直。字形沿螺旋变大，第一个是尾部最后一个的一半；
间距不均匀以适配尺寸差；螺旋周期按所需长度调整，旋转使尾部位于左侧中部。

> 这条对解码最重要：几何还原和语义解码可以拆成两个独立问题。

### ✅ handwriting / seed 影响哪一层

博客只提到「可配置的手写模式模拟手写的不精确程度」，没讲实现，也没提 seed。
实测结论见下节。

### 其它

作者提到挪麦对话是**树结构**而非线性，用**分支螺旋**表示一来一往。
但技术实现部分没写编码层怎么处理多句与分支。

**作者全文没有讨论解码或可逆性。**

## 已答：seed / handwriting 只作用在笔画层

2026-08-31 实测，固定 message 与 base，统计返回 SVG 里的 `<path>` 数量：

| message | seed | base | handwriting | paths |
|---|---|---|---|---|
| hello | 0 | 200000 | 0.3 | **107** |
| hello | 47 | 200000 | 0.3 | **107** |
| hello | 999 | 200000 | 0.3 | **107** |
| hello | 47 | 200000 | **0.0** | **107** |
| hella | 47 | 200000 | 0.3 | 101 |
| hi | 47 | 200000 | 0.3 | 48 |
| hello | 47 | **256** | 0.3 | 53 |

**结论：** 三个不同 seed、以及 handwriting 归零，path 数都是 107；改一个字母立刻变 101。
seed 与 handwriting 只改坐标抖动，不改结构。

**推论：**

1. 给定 `(message, base)`，结构唯一 → 解码是**精确逆运算**，不是模糊识别
2. 解码必须知道或推断出 `base`
3. `seed` 可当**数据增强旋钮**：同一文本换 seed，标签不变、笔迹不同，
   用来造识别模型的鲁棒性样本，成本为零

对比样本见 `assets/samples/hello_base200000_seed47.svg` 与 `..._seed48.svg`。

## 解码路线（2026-08-31 推导）

```
图像 → 螺旋还原成矩形 GlyphGrid → 读出每步选择 → 反推大整数 x → 按 base 拆成码点
```

**为什么在数学上可行：** Oracle 正向是 `answer = x mod k; x //= k`，
反向就是 `x = x·k + answer`——从最后一次选择倒推回第一次即可重建 x。
所以解码是精确逆运算，不是概率识别。

**陷阱：** 每次询问的 `k` 取决于生成算法当时的状态，而状态又取决于之前的答案。
所以解码器**不能查表**，必须跟着原生成逻辑走一遍，每到决策点用图像里读到的
实际答案代替 Oracle 的输出。本质是「逆向执行那个生成器」。

→ 仍然要读 Julia 源码，但目的变了：不是搞懂编码，是**复现决策序列**。

**还需要知道 base。** 不知道的话可以试常见值（256、200000），
或从字形数量反推。
